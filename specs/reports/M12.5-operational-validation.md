### 4.3 TF-IDF Similarity Observations

- **Self-match similarity:** ~0.05 for "Update README with installation instructions" vs goals with capability-heavy vectors
- **Cause:** TF-IDF vectors include capability terms (`mcp:filesystem.read_file`, etc.) which dilute title-based similarity
- **Impact:** Low similarity scores don't indicate poor retrieval — they indicate the index is correctly accounting for capability context
- **Recommendation:** For M13, consider separate title-only and capability-only indexes, or switch to embedding-based retrieval

## 5. Observations

### What worked well

1. **Append-only timeline is trivially testable.** Concurrent writes, immutability, and persistence all verified without complex setup.

2. **Pattern mining produces actionable results.** 6 identical workflows → frequency=6, success_rate=1.0 → reliable pattern → suggestion with reasons. The pipeline works.

3. **Replay classification is accurate.** Steps are correctly classified as reused/adapted/skipped/new based on position changes. The `reuse_ratio()` and `adaptation_ratio()` metrics are meaningful.

4. **Graceful degradation is real.** Sparse history doesn't crash, doesn't produce false positives, and returns low-trust evidence. The system benefits from history but doesn't depend on it.

5. **ADR-0009 contract holds.** Experience returns evidence (similarity, trust, outcome, reflection), never decisions. Scenario 7 confirms multiple pieces of evidence are presented, not a single "best" match.

### What was surprising

1. **TF-IDF dilution by capability terms.** The semantic index mixes title and capability terms into a single vector. This makes title-based queries less effective when capabilities dominate the vector. Not a bug — an observation about the current indexing strategy.

2. **`successful_workflows()` sensitivity to query phrasing.** The method filters by `text_similarity > 0.1`, which can exclude matches when capability terms dilute the vector. The planner should use `similar()` as the primary query and `successful_workflows()` as a secondary signal.

3. **Concurrent writes are safe.** The redb database handles concurrent appends correctly. No deadlocks, no corruption, no lost entries. The `Mutex<Database>` serialization is sufficient.

## 7. Issues Found

### 7.1 TF-IDF Dilution (Low Severity)

**Observation:** Title-based similarity is diluted when capability terms dominate the goal vector.

**Impact:** `similar()` and `successful_workflows()` may return low scores for queries that match on title but not capabilities.

**Recommendation:** Defer to M13. Consider:
- Separate title-only index for title queries
- Embedding-based retrieval (replacing TF-IDF)
- Configurable query-time weighting

### 7.2 No Real-Repository Dogfooding (Medium Severity)

**Observation:** All scenarios are synthetic. Real repositories (FRIDAY itself, other Rust crates) were not exercised.

**Impact:** Edge cases in naturally evolved history (messy commits, partial failures, branching workflows) are not tested.

**Recommendation:** Before M13, run the experience pipeline against FRIDAY's own git history to validate retrieval quality with real data.

### 7.3 `successful_workflows()` Query Sensitivity (Low Severity)

**Observation:** The method's `text_similarity > 0.1` threshold can exclude matches when the query doesn't overlap with capability terms.

**Impact:** Planner may miss successful workflows if the query phrasing doesn't match the goal title closely enough.

**Recommendation:** Defer to M13. Consider lowering the threshold or using `similar()` as the primary discovery mechanism.

## 8. Recommendations for M13

Based on operational validation findings:

1. **Planner integration.** Enrich `PlanningContext` with `ExperienceMatch` evidence. The experience layer is validated; the planner should consume it.

2. **Embedding-based retrieval.** Replace TF-IDF with embeddings to resolve dilution issues and enable semantic similarity beyond keyword overlap.

3. **Real-repository dogfooding.** Run the experience pipeline against FRIDAY's own history. Measure retrieval precision with naturally evolved data.

4. **Timeline compaction.** The append-only timeline grows without bound. A retention policy (e.g., keep last 1000 goals, compact older entries) is needed.

5. **Adaptive trust calibration.** The current trust weights (similarity 30%, outcome 40%, recency 20%, repetition 10%) are static. Observe real usage before tuning.

## 9. Deferred Improvements

These are known improvements that should NOT be implemented until real-repository dogfooding provides evidence:

- Embedding-based retrieval (replacing TF-IDF)
- Adaptive trust calibration (learning weights from outcomes)
- Replay optimization (step-level provenance, not just position-based)
- Learned suggestion policies (beyond frequency/success thresholds)
- Separate title-only and capability-only indexes
- Timeline compaction / retention policy
- Push notifications for relevant new experiences
- Experience-driven capability discovery
